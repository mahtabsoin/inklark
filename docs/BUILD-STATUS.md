## Current preview

The original editor remains at its existing address. After restarting the local launcher, the new device-approval preview is available at `http://localhost:4319/sign.html`. `localhost` is required for the local WebAuthn relying-party domain; the launcher's privileged broker endpoints remain restricted to their original `127.0.0.1` origin.

The preview adopts a typed name, enrolls and verifies an ES256 credential, and prepares a sample document with a signature location. **Sign this document** authenticates once and downloads the exact output whose hash was approved. **View document** is optional. An approval record can be downloaded separately. Requests with flagged answers require explicit acknowledgement first. The preview is separate from the existing image-vault editor, whose controls are unchanged.

Setup uses two WebAuthn ceremonies once: credential creation, followed by proof of possession of the public key returned by the browser. Later signing uses one authentication ceremony. Credential registration is un-attested; it does not establish legal identity or certify a hardware model. Keys and profiles remain inside the trusted-browser/device boundary.

`npm run test:device` uses a fresh Playwright context and a virtual CTAP2 authenticator. It checks persistent key storage, encrypted decryption, real signed assertions, replay refusal, canceled authentication and retry, changes during authentication, a mobile viewport, optional preview, and a downloaded PDF whose hash matches its approval record. It does not operate a real person's credential.

Enrollment evidence now binds the full stable public device description, including its encryption key, credential ID, signer name, and appearance revision. Tests reject substitutions of those fields. Approval proof, one-use nonce, and the monotonic authenticator counter are committed in one IndexedDB transaction. Injected storage failure leaves the nonce unused; concurrent approvals preserve the newest counter.

Live authorization and historical evidence verification use separate functions. Historical verification checks the pinned signature binding and explicitly reports that it grants no fresh authorization. It cannot establish a trusted signing time. Encryption has a 45 MiB plaintext-envelope limit so a supported 30 MiB PDF still fits after base64 encoding and request overhead; the large-envelope regression test encrypts and opens that payload. The relay still needs matching limits and storage behavior.

## Next implementation step

Build the durable relay and remote MCP endpoint around the shared request encryption and approval checks. Verify credential enrollment on the relay, bind its pairing to the device delivery key, and store only encrypted document payloads. Then connect the signing preview to request delivery and prove a live cloud-agent call before labeling the release ready for user testing.

A Sites hosting project has been registered and its identity is persisted in ignored local hosting state. It has no deployed version yet. The supported source helper failed to connect to its Git hosting endpoint under this task's network restrictions. Reuse that project when publication becomes available; creating another project would not solve the connection failure.

The local executor currently rejects npm registry network connections. No new packages were installed. The initial ES256 verifier deliberately supports a narrow subset using native Web Crypto and validates the expected origin, relying-party hash, credential ID and optional user handle, presence/verification flags, backup flags, signature counter, challenge, expiry, and signature. It does not implement authenticator attestation policy, certificate-based PDF signatures, or universal identity verification. Keep this implementation subject to security review before recommending it for sensitive documents.
